## 3. Signing config safety

`mobile/build.gradle:52-58`:

```groovy
release {
    def releaseKey = file("${rootDir.getAbsolutePath()}/keys/release-keystore.jks")
    storeFile = releaseKey.exists() ? releaseKey : debugKey
    storePassword = System.getenv("STORE_PASS") ?: "debugkey"
    keyAlias = System.getenv("KEY_ALIAS") ?: "transtracks"
    keyPassword = System.getenv("KEY_PASS") ?: "debugkey"
}
```

🟠 **Risk #1**: Silent fallback to the debug keystore if the release keystore file is missing.
🟠 **Risk #2**: Silent fallback to the debug password if env vars are missing.

The result: a developer running `./gradlew :mobile:bundleRelease` locally without env vars produces an
AAB signed by the debug keystore with the alias `transtracks`. Play upload will reject it (different
fingerprint), so the worst case is "wasted CI minutes". However:

- 🟠 The artifact gets named `mobile-release.aab` and *looks* indistinguishable from the real one.
- 🟠 If a developer ever sideloads / shares this AAB, it would install fine on a clean device with the
  same fingerprint as their personal debug builds — confusing.

🟢 The keystore file itself is correctly excluded from git (`.gitignore`).

🟠 **Recommendation**: convert the silent fallbacks to `throw new GradleException("Release keystore missing")`
when the active task is `bundleRelease` or `assembleRelease`.

## 5. Mobile + Wear release coupling

🔴 **Currently broken / asymmetric:**
- `:mobile:bundleRelease` is built and uploaded.
- `:wear:bundleRelease` is **not built and not uploaded**.

The implication is that `production` pushes ship a phone-only update, with the (broken) Wear app left
at whatever version was last uploaded manually — if any.

For a tethered Wear app with a `play-services-wearable` data contract, **the two should ship together
or at least use a strict version-skew policy**. Today there is no policy.

🟠 **Question**: how was the Wear app initially published to Play Console? If it never was, then the
`standalone=false` declaration in the wear manifest will simply prevent Play Store from installing the
wear app at all when the user installs the mobile app. (See `MONOREPO.md` for the intended distribution
model.)

🟠 **Recommendation**: 
1. Add `:wear:bundleRelease` to the deploy step.
2. Use Play's "Wear OS" tab to bundle the wear AAB with the mobile listing (Auto-install on connected
   watches) — no separate Play Store listing needed.
3. Tie wear `versionCode` to mobile `versionCode` programmatically so they never drift.

## 6. Versioning strategy

`mobile/build.gradle:19-29`:
```groovy
def major = 1
def minor = 3

def getVersionCode = { ->
    def envBuildNumber = System.getenv("BUILD_NUMBER")?.toInteger() ?: 0
    def baseBuildNumber = 25
    return baseBuildNumber + (major * 100) + minor + envBuildNumber
}
def getVersionName = { ->
    return "$major.$minor.${getVersionCode()}"
}
```

So a CI build with `BUILD_NUMBER=42` becomes `versionCode = 25 + 100 + 3 + 42 = 170`,
`versionName = "1.3.170"`.

🟢 **Strengths**:
- Monotonic by `BUILD_NUMBER` (CI run number), so versionCode only ever goes up.
- Human-readable major.minor in the name.
- Tag is `v1.3.170` (auto-tagged in `ci.yml:91-98`). ✅

🟠 **Weaknesses**:
- `versionCode` formula has 3 magic numbers (`baseBuildNumber=25`, `major*100`, the multiplication).
- `wear/build.gradle:32-33` hard-codes `versionCode 1` / `versionName "1.0"` — completely
  disconnected from the mobile versioning scheme.

🟠 **Recommendation**: have `wear/build.gradle` import the same `getVersionCode()` function (or move
the function to a `buildSrc` extension) so the two stay aligned.
